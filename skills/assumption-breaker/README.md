# assumption-breaker

## 概要

RFC、提案書、brief、Slack 投稿などのテキストを渡すと、提案者が当然としている前提を洗い出し、それぞれを外した代替解とトレードオフ付きの推奨を返す。説得術ではなく発想法で、見えていなかった解の空間を可視化する。

## 利用メリット

- ひとつの提案に固まった議論から、具体的な別解が並ぶので、PoC 前に選択肢を見比べられる。
- 「なぜそうなの？」が言葉になり、チームで前提を疑える。
- 別解の得失が明示されるので、ラディカルな組み合わせと元案に近い解を選びやすい。

## 利用シーン

- RFC や提案を受け取って、他の解き方がないか考えたいとき
- 「なぜそうなの？」が気になるが、何を疑えばいいかわからないとき
- チームの思考がひとつの方向に固まっているとき

依頼の例: 「この提案の前提を疑って」「別の解き方ない？」

## 使い方

**いつ使うか:** RFC や提案がひとつの解き方に固まったとき、PoC の前に選択肢を並べたいときに入る。市場地図そのものが主題なら `market-landscape`、残した方向を一文にするなら `product-vision-and-concept`。

1. ユーザーが対象テキストを渡す。スキルが課題、ほしいもの、制約、暗黙の前提に分ける。
2. スキルが疑うべき前提のリストを出すので、ユーザーが追加・修正してから次へ進む。
3. スキルが前提ごとに反転し、代替解とトレードオフを出す。最後に組み合わせ解と、インパクト・ラディカル・穏当の推奨 3 つ、著者への問い返しを並べる。残した仮説は `uncertainty-map` へ落とせる。

## 具体例

依頼: 「この提案の前提を疑って。社内公募アプリで応募率を上げる、と書いてある。」

::: info 出力される前提リストの抜粋:

| # | 前提 | レンズ |
|---|---|---|
| 1 | 応募率が低いのは、募集を知らないからだ | プロセスの固定 |
| 2 | 社内公募アプリを出せば手が挙がる | 手段の固定 |
| ... | ... | ... |

| # | 代替解 | 崩した前提 | 使ったムーブ |
|---|---|---|---|
| A | 募集を増やす前に、手を挙げる瞬間だけ匿名にする | #2 | 手段と目的の分離 |
| ... | ... | ... | ... |

:::

## 構成

```text

├── README.md
├── SKILL.md
├── templates/
│   └── docs/
│       ├── index.md       # 打ち合わせ用 Markdown の型（prhythm-docs が埋める）
│       └── sections.html  # スライド本体の型
└── references/
    ├── thinking-moves.md   # 前提を崩すときの思考ムーブ
    └── output-format.md    # 統合・評価の出力フォーマット
```

## 前提条件

- 対象となる RFC、提案、brief などのテキスト。

## 注意事項

- 元案を全否定するためのスキルではない。前提を外すのは解の空間を広げるためで、代替解は具体とトレードオフまで書く。
