# product-vision-and-concept

## 概要

プロダクト名（あれば）、概要、使う言語を渡すと、対話で素材を引き出し、複数案を見比べて磨き込んだ一行ステートメントと Why / Who / What / How it's different の最終稿を返す。既存のビジョン文を貼れば、弱点と改善方向の診断から入る。

## 利用メリット

- 代わりに書かれた文案ではなく、対話を通じて自分たちの言葉で説明できるようになる。
- 一行と詳細コンセプトが揃うので、チームの判断基準を一本にしやすい。
- 2〜3 案と統合案を見比べるので、欲しいトーンや粒度がはっきりする。
- PRD の導入に転用できる粒度まで整う。既存文案なら、弱点が具体的に分かる。

## 利用シーン

- プロダクトを一言で言えず、機能説明に逃げがちなとき
- チーム内で方向性の認識がバラバラなとき
- ペルソナや JM のインサイトは揃ったが、一行に落ちていないとき
- 書いたビジョンを第三者目線で見てほしいとき

依頼の例: 「Feedit のビジョンを一緒に作って」「この一文、どう思う？ 改善したい」

## 使い方

**いつ使うか:** プロダクトを一言で言えず、チームの北極星がバラバラなときに入る。`market-landscape`、`defining-personas-and-segments`、`create-journey-map` のあとが多い。スキーマや画面の前に Why を固める。既存文案の診断だけでも使える。

**新規に言語化する**

1. ユーザーがプロダクト名と言語（日本語 / 英語）を渡す。分かっている範囲の概要でよい。
2. スキルが質問で素材を引き出し、2〜3 パッケージと統合案を出す。ユーザーが近いものを選ぶ。
3. スキルがトーンや長さを直し、一行と Why / Who / What / How の最終稿と品質チェックを出す。

**既存文案を見る**

貼ったビジョンの診断から入り、弱点と改善方向を出したあと、必要なら推敲へ戻る。

## 具体例

依頼: 「社内公募アプリのビジョンを一緒に作って。部署を越えた手挙げが起きるようにしたい。」

::: info 出力される最終稿:

| 項目 | 内容 |
|---|---|
| 一行ステートメント | スキルに合うミッションが向こうから届き、匿名の一歩で越境が始まる。 |
| Why | 社内公募の制度はあるが、応募率は 1.2%。募集を見ても、手を挙げる瞬間に「今の部署にどう思われるか」が先に来る。 |
| Who | 営業企画の佐藤さん（入社 5 年）。部署外の仕事に興味はあるが、名前が出る応募は避ける。 |
| What | 探しに行かなくても、スキルタグに合うミッションが手元に届く。本名を出す前に近づける。 |
| How it's different | イントラ掲示板やタレントマネジメントは「掲載して待つ」。ここでは募集が向こうから届き、合意のあとで初めて名前が出る。 |

:::

## 構成

```
product-vision-and-concept/
├── README.md
├── SKILL.md
├── templates/
│   └── docs/
│       ├── index.md       # 打ち合わせ用 Markdown の型（prhythm-docs が埋める）
│       └── sections.html  # スライド本体の型
└── references/
    ├── frameworks.md    # 一行と Concept の書き方
    ├── examples.md      # 良い例と悪い例
    └── antipatterns.md  # 失敗パターン（品質チェック用）
```

## 前提条件

- 分かっている範囲のプロダクト概要（名前、ターゲット、課題など。未確定部分は `(仮)` で進む）。

## 注意事項

- 回答が薄くても進める。未確定部分は `(仮)` と明示し、後から差し替えられる。セッション終了時は一行と Concept の最終稿、品質チェックを必ず出す。
