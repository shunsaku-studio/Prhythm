# assumption-breaker Document Format

Use this template when formatting output from the `assumption-breaker` skill into a document file.

The key structural principle: **推奨 3 picks と問い返しが先、前提抽出と代替解の詳細は後。**

---

## Template

```markdown
# {Topic / RFC Title} — Assumption Breaker

## Input Frame

| Field | Content |
|-------|---------|
| **Source** | {RFC / 提案 / brief — 出典を1行で} |
| **課題（原文要約）** | {RFCが述べている課題を1–2文で} |
| **求められている解** | {RFCが提案している解決策を1–2文で} |
| **明示制約** | {予算、期限、技術スタック等} |

---

## 推奨 3 picks

{読み手がまず見るセクション。全体を読まなくてもアクションが取れるように。}

### 🎯 最もインパクトが大きい: {解の名前}

{1–2文。なぜインパクトが大きいか。崩した前提を明記。}

### 🚀 最もラディカル: {組み合わせ解の名前}

{1–2文。何がラディカルか。組み合わせた前提崩しを明記。}

### 🔧 最も穏当（前提を1つだけ外す）: {解の名前}

{1–2文。元RFCからの変更が最小限であること。}

---

## 元RFCへの問い返し

{代替解の押し売りではなく、著者が自分で前提を再考するきっかけになる問い。2–3個。}

1. **{問い}** — {なぜこの問いが重要か、1文}
2. **{問い}** — ...
3. **{問い}** — ...

---

## 暗黙の前提（N個）

| # | 前提 | レンズ | なぜこれを前提と判断したか |
|---|------|--------|--------------------------|
| 1 | {前提} | {レンズ名} | {根拠} |

### レンズ凡例

| レンズ | 走査する観点 |
|--------|-------------|
| 手段の固定 | 「Xが必要」は手段であって目的ではないか |
| ユーザーの固定 | 誰が使うかの思い込み |
| プロセスの固定 | 現行ワークフローへの依存 |
| 技術の固定 | 暗黙の技術スタック前提 |
| 品質基準の固定 | 「品質」の定義が曖昧なまま合意 |
| スコープの固定 | 解決範囲の広さ/狭さの思い込み |

|---|--------|-----------|-------------|-----------|-----------|------|
| A | {名前} | #{前提番号} | {ムーブ名} | 高/中/低 | 高/中/低 | 近/中/遠 |

### 組み合わせ解

| # | 組み合わせ名 | 含む代替解 | 何が変わるか |
|---|-------------|-----------|-------------|
| X | {名前} | {A + C} | {1文} |

{前提ごとにグループ化。各代替解の詳細を記載。}

### 前提 #{N}: {前提の内容}

#### 代替解 {letter}: {解の名前}

{次の前提グループへ。全前提を繰り返す。}

---

- {検証が必要な前提や仮説}

- {この分析を踏まえた推奨アクション}
```

## Formatting rules

- **推奨 3 picks が最初。** 読み手の最初の問いは「で、どうすればいい？」であって「どんな前提があった？」ではない
- **問い返しセクションは推奨の直後。** 代替解を押し付けるのではなく、対話を開くのがこのスキルの本質
- **代替解マップ表がアンカー。** 1つだけ見るならこの表。全代替解をインパクト/難易度/距離で俯瞰できる
- **代替解詳細は前提ごとにグループ化。** 時系列（Phase 2の実行順）ではなく前提軸で整理する
- **組み合わせ解は必須。** 単体の代替解列挙だけで終わらない。前提崩しの掛け算が最も価値が高い
- **Gaps & Next Steps で閉じる。** 前提崩しは一回で終わらない。次に検証すべきことを明示する

## Anti-patterns

- 代替解詳細が先、推奨が後（読み手が迷子になる）
- 暗黙の前提テーブルにレンズ名がない（再現性がなくなる）
- 代替解が抽象的（「別のアプローチ」はNG。具体的な技術・UX・プロセスを書く）
- トレードオフが書かれていない（バラ色の妄想になる）
- 組み合わせ解がない（前提を1個ずつ崩すだけでは面白い解が出ない）
- 問い返しが代替解の言い換えになっている（問い返しは疑問形であること）
