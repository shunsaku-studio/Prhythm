# Slide grammar — prhythm-docs

スライドが「ダサい・伝わらない」原因はほぼ 3 つに集約される。**結論の一文が無い / 情報量が野放し / 見出しが体言止め**。この 3 つを構造で禁止するのがこの文法。

デザイン（CSS・ビューア）は [deck-shell.md](deck-shell.md) が持つ。ここは **何を何文字で書くか**だけを扱う。

---

## 1. メッセージライン必須

各スライドの `h2.msg` は、そのスライドで言いたいことを **1 文** で書く。セクション名は `.eyebrow` に降ろす。

```html
<!-- NG: 体言止め。見出しを読んでも何も分からない -->
<div class="eyebrow">Frame</div>
<h2 class="msg">Research Frame</h2>

<!-- OK: 読んだだけで主張が伝わる -->
<div class="eyebrow">Frame<span class="sep"></span>market-landscape</div>
<h2 class="msg">調査は個人向け家計アプリに絞る。法人会計と証券は今回見ない。</h2>
```

ルール:

- **30〜60 字**。短すぎると中身がなく、長すぎると読まれない
- **句点で終わる**。体言止め・名詞句は禁止
- 数字・固有名詞を入れる。「多くの課題がある」ではなく「7 社中 5 社が手入力で詰まる」
- 強調は `<span class="em">`（アクセント色）か `<span class="mark">`（下線ハイライト）を 1 スライドに 1 箇所まで

下の本文は **メッセージラインの根拠** だけを置く。メッセージラインと無関係な情報が載っているなら、それは別スライド。

---

## 2. デッキ構成は 6〜8 枚で固定

```
Cover → Frame → Answer → Evidence (1–2) → Gates → Next
```

| 枚 | 役割 | レイアウト | 中身 |
|----|------|-----------|------|
| Cover | 表紙 | `s-cover` | テーマ・一行文脈・出典と日付 |
| Frame | 何を見て何を見なかったか | `rows` / `table.t` | スコープ・前提・モード。4〜5 行 |
| **Answer** | **で、何？** | `s-statement` | **結論 1 文 + 根拠 2〜3 行。これが無いデッキは不合格** |
| Evidence | 結論を支える材料 | `tracks` / `table.t` / `quadrant` / `split` | 1〜2 枚。カタログ全量は載せない |
| Gates | 人間が決めること | `bullets numbered` | 3 つまで。疑問形で書く |
| Next | 次にやること | `rows` / `bullets` | 3 つまで。動詞で始める |

Answer は Evidence より **前**。旧テンプレは Synthesis が 3 枚に散っていて結論スライドが存在せず、これが「クリアに伝わらない」の直接原因だった。

Evidence を 3 枚以上に増やしたくなったら、それは元スキルの `docs/` 成果物やチャットに置くべき情報。デッキには載せない。

---

## 3. 情報量バジェット

`lint-deck.mjs` が機械的に検査する。超えたら **削る**（フォントを縮めない — 1920×1080 固定キャンバスなので縮小は等倍で全部小さくなるだけ）。

| 対象 | 上限 |
|------|------|
| メッセージライン `.msg` | 30〜60 字・句点終わり |
| Answer の `.statement` | 20〜80 字 |
| Answer の `.because` | 3 行・各 60 字 |
| `.tracks` | 4 本 / `.tlabel` 14 字 / `.tbody` 70 字 |
| `.rows` | 5 行 / `.rk` 16 字 / `.rv` 80 字 |
| `table.t` | 6 行 × 4 列 / セル 40 字 |
| `.bullets` | 5 個 / 各 50 字 |
| `.qitems` | 1 象限あたり 4 個 / `.qitem` 18 字 |
| 軸ラベル `.qy` / `.qx` | 端ラベル 8 字 / 軸名 10 字（折り返さない） |
| スライド全体 | 400 字 |
| デッキ全体 | 8 枚 |

`?debug` を付けてブラウザで開くと、はみ出しているスライドが赤枠になり、コンソールに超過 px が出る。

---

## 4. プレースホルダは枠付きで書く

テンプレのプレースホルダは `{{NAME}}` 形式。**リストやテーブルを丸ごと 1 プレースホルダにしない** — 件数の制約が消え、埋める側が無限に詰め込む。

```html
<!-- NG: 何個入るか分からない -->
<ul class="bullets">{{GATES}}</ul>

<!-- OK: 3 個と決まっている -->
<ul class="bullets numbered">
  <li>{{GATE_1}}</li>
  <li>{{GATE_2}}</li>
  <li>{{GATE_3}}</li>
</ul>
```

埋める材料が足りない行は、**プレースホルダを残さず `<li>` ごと削除**する。`{{GATE_3}}` が残ったまま出力されたら build 時に警告が出る。

---

## 5. レイアウト部品の選び方

| 出したいもの | 使う部品 |
|-------------|---------|
| 結論 1 文 | `s-statement` + `.statement` + `.because` |
| 3〜4 個の並列概念、フェーズの流れ | `.tracks.n3` / `.n4` |
| 項目と説明のペア | `.rows` |
| 比較・一覧 | `table.t` |
| 主張と根拠の対比、As-Is / To-Be | `.split` |
| ポジショニング、2 軸マッピング | `.quadrant`（**mermaid の quadrantChart は使わない**） |
| Gates の 3 つの決断 | `.bullets.numbered.lg` |
| ER 図 / ユースケース図 | `.diagram > pre.mermaid` |

`.quadrant` は右上を狙う象限として `is-target` を付ける。自案は `.qitem.own`。

mermaid は **ER 図とユースケース図の 2 用途だけ**。ジャーニーのフェーズや工程は `.tracks` の方が読みやすく、mermaid の flowchart は横に間延びして小さくなる。図が無いデッキには mermaid の CDN 自体が注入されない（`build-deck.mjs` が `.mermaid` の有無で判定する）。

---

## 6. 禁止

- 体言止めの `h2`
- Answer スライドの無いデッキ
- カタログ・質問プール・AC の全量転記
- `clamp()` / `vw` / `vh` をスライド CSS に書くこと（固定キャンバスの前提が壊れ、lint が効かなくなる）
- 絵文字装飾
- スキル出力に無い断定
