# スキル集 README 執筆・推敲原則

スキル集の各 README を書く・直すときの原則。LLM への修正プロンプトとしてそのまま貼り付けて使えるよう、判定基準と禁止事項を明文化してある。

---

## 0. 修正プロンプトとしての使い方

> あなたはスキル集のドキュメント(README)を推敲する編集者です。以下の原則に従って対象の README を書き直してください。見出し構成は維持し、中身を原則に沿って修正します。原則同士が衝突した場合は「大原則」を優先してください。

---

## 1. 大原則

### 1-1. 読者はユーザーであり、関心は「自分の作業がどう楽になるか」

README はスキルの内部設計を解説する文書ではない。設計の巧みさ(責務分離、モード構成、他スキルとの構造的類似)に読める記述は、ユーザーの便益か具体的な使い方に翻訳するか、削除する。

### 1-2. ただし、便益の強調はコピーライティングではない

「ユーザー視点」を「刺さるフレーズを作ること」と解釈しない。キャッチコピー的な圧縮文体・スローガンの連呼は、設計自慢と同じくらい読者の理解を妨げる。目指すのは、初見の読者が一読して次の行動を想像できる**平易な説明文**である。

### 1-3. 各セクションは固有の情報を運ぶ

同じ内容(同じキーワード、同じ売り文句)をセクションを変えて言い換え再掲しない。各セクションの役割は次の通りで、他のセクションの役割を侵食しない。

| セクション | 運ぶ固有情報 |
|---|---|
| 概要 | このスキルが何をするか(入力→出力) |
| 利用メリット | なぜ手作業や素の LLM より嬉しいか |
| 利用シーン | どんな状況で思い出せばよいか |
| 使い方 | 実際にどう進むか(手順) |
| 具体例 | 出力がどんな粒度・文体で出てくるか(中身の抜粋) |
| 前提条件 | 起動時に何が必要か |
| 注意事項 | 使って初めて気づく非自明な落とし穴 |
| 関連スキル | どの場面で他スキルへ移るか |

推敲時の判定: あるセクションを丸ごと削除しても読者が失う情報が無いなら、そのセクションは言い換え再掲になっている。

## 2. 文体原則

### 2-1. 完結した文で書く

「**太字フレーズ** — 断片」の電報調を README の標準文体にしない。箇条書き自体は使ってよいが、各項目は主語と述語のある読み下せる文にする。

- 悪い例: 「**空白の右上が議論できる** — 混雑地帯と未開拓地帯が地図上で見える」
- 良い例: 「参考サービスを地図上に並べるので、競合がひしめく領域とまだ誰もいない領域をチームで議論できる」

矢印記法(「カタログ → 軸候補 → マップ」)も内部仕様書の圧縮記法なので使わない。流れは文か番号付き手順で書く。

### 2-2. 否定形で挙動を説明しない

「〜は分析しない」「〜を主目的にしない」のような否定形・内部規律の言い回しは認知負荷が高い。時系列に沿った肯定形に直す。

- 悪い例: 「会議そのものがゲートで、mode:prep は分析せず、会議後に初めて mode:analysis へ進む」
- 良い例: 「会議前に mode:prep でヒアリング項目を洗い出し、会議後に mode:analysis でボトルネック仮説を整理する」

「ゲート」「責務」「モード判定」といった設計内部の用語は README では使わない。

### 2-3. 独自用語・比喩は初出で一度定義し、連呼しない

スキル固有の造語(例: 「空白の右上」)は、初出時に一度だけ普通の日本語で定義する(例: 「軸の右と上を望ましい方向に取ったとき、まだどのサービスも立っていない領域。本 README では『空白の右上』と呼ぶ」)。定義後も、スローガンとして各セクションで繰り返さない。文書全体での登場回数の目安は 2〜3 回。

### 2-4. 手順は行為者を主語にする

「軸候補が出る」のような主語のない受け身は、ユーザーが何をしてスキルが何をするのか分からない。

- 悪い例: 「軸候補が出る。チームが軸を確定してから地図に進む」
- 良い例: 「スキルが軸の候補を複数提示するので、チームで 1 組選ぶ。選んだ軸で次のステップに進む」

### 2-5. 内輪の速記を因果のある文に開く

チーム内では通じる省略表現は、初見の読者に向けて因果を書き下す。

- 悪い例: 「非公式チャネル(Slack 等)を忘れると、右上が偽って空く」
- 良い例: 「Slack ボットのような非公式チャネルで提供されるサービスは Web 検索から漏れやすい。調査に含め忘れると、実際には競合がいる領域が空白に見えてしまう」

判定基準: その一文だけを文書から切り出して、文脈なしで意味が取れるか。

## 3. セクション別原則

### 概要

- 最初の 2〜3 文で「何を入力すると何が出てくるか」が分かること。
- 他スキルへの言及は、作業が直列する(前後工程になる)など関連が本当に深い場合のみ。「〜と同様の構成」のような設計上の類似への言及は削除する。
- 独自用語を使うならここで定義する(2-3 参照)。

### 利用メリット

- ユーザーが最初に抱く関心・悩みに対する便益を書く。「このスキルを使わなかった場合との差」が読み取れること。
  - 良い例: 「初めてのヒアリングでも、重要な点を押さえた質問紙を準備できる」
- スキル内部の設計特性(一本化される、責務が混ざらない、再利用が効く)はメリットとして書かない。残したい場合は、それがユーザーの何を楽にするかに翻訳する。
- 概要と同じ内容の言い換えになっていないか確認する(1-3 参照)。

### 利用シーン

- ユーザーが実際に置かれる具体的な状況だけを書く。
  - 良い例: 「初回ヒアリング前に何を聞くか整理したいとき」
- スキルのモード構造や設計から逆算した抽象的なシーン(例: 「どちらのモードから始めるか曖昧なとき」)は削除する。
- 「依頼の例」として、ユーザーが実際に打ち込む文を 1〜2 個添える。

### 使い方

- タイミングは工程に対して明確に書く(例: 「会議前に mode:prep を、会議後に mode:analysis を使う」)。
- 手順は番号付きで、各ステップの主語を明示する(2-4 参照)。
- プロセス途中の条件・チェックポイント(例: 「軸に合意してから地図に進む」)は、前提条件ではなくここの該当ステップに書く。

### 具体例(独立セクション。「使い方」の直後に置く)

- 依頼文 1 つと、成果物の中身の抜粋のペアで構成する。
- 抜粋とは、出力の種類の列挙(「アクター一覧、表、Mermaid 図が出る」)ではなく、出力そのものの一部を指す。実際の名前が入った表の 2〜3 行、成果物中の一文、数行の図など。読者が「この粒度・この文体で出てくるのか」を掴めることが目的。
  - 悪い例: 「返ってくるもの: アクター一覧、機能とユースケースの表、Mermaid の全体図」(概要と手順の言い換えであり、固有情報が無い)
  - 良い例: 「出力される docs/usecase-map.md の抜粋:
    | 月次レポート | 品質管理部長が、各ラインの検査データを集計してレポート草稿を得る |」
- 判定基準: 具体例のセクションを丸ごと削除したとき、読者が「出力の粒度と文体」を想像する手段を失うか。失わないなら、その具体例は種類の列挙になっている。
- 表と Mermaid はコードブロック（```markdown）で囲まない。ドキュメントサイトが表と図として描画できるよう、素の Markdown 表と ```mermaid フェンスで書く。抜粋は VitePress の `::: info 出力される {path} の抜粋:` で囲み、「〜の抜粋:」をコンテナのタイトルにする（INFO のままにしない）。抜粋の中では `##` / `###` を使わず太字にする（ページ目次を汚さない）。コード（SDL、ディレクトリツリー）だけフェンスを残す。表を抜粋するときは、末尾に各列 `...` の行を足して続きがあることを示す。
- スキルが example.md を持つ場合の役割分担: README の具体例は粒度が伝わる最小の抜粋にとどめ、末尾で example.md へリンクする。全文は example.md に置く。

### 構成(ファイルツリー)

- ツリーはそのまま載せてよい。コメントは「モデルが読む本体」のような内部視点ではなく、ユーザーがカスタマイズや deep dive したくなったときの道標として書く。

### 前提条件

- スキルの**起動時に必須(required)**な入力・環境・条件だけを書く。
- スキル集全体で自明な前提(実行環境が Claude Code / Cursor であること等)は書かない。
- 「〜でも使ってよい」のような許可の記述は書かない。使うかどうかはユーザーが決める。
- 断片で書かず、何がどう必要なのか文で書く(悪い例: 「Web 検索(日英)」/ 良い例: 「日英での Web 検索が実行できる環境が必要」)。
- プロセス途中の条件はここに書かない(「使い方」へ移す)。

### 注意事項

- 他セクションを読めば分かることの繰り返しは削除する。
- 実際に使って初めて気づく非自明な落とし穴だけを残し、因果を文で書く(2-5 参照)。
- 残すものが無ければ、セクションごと削除してよい。空欄を埋めるために自明な注意を書かない。

### 関連スキル

- スキル名には該当 README への相対リンクを張る(例: `[create-journey-map](../create-journey-map/README.md)`)。
- 関係の説明は「どういう場面でそちらへ移るか」が分かる書き方にする。「補完」「後続」のような分類語だけで済ませない。

## 4. 推敲チェックリスト

書き終えたら(または修正させたら)以下で検査する。

1. **設計自慢テスト**: スキルの作者しか嬉しくない記述(構成の巧みさ、責務分離)が残っていないか。
2. **重複テスト**: 概要・メリット・シーンから 1 セクションを消しても失われる情報が無い、という状態になっていないか。
3. **初見テスト**: 独自用語が定義前に使われていないか。定義後に連呼されていないか。
4. **文テスト**: 「太字+ダッシュ+断片」や矢印記法が説明の主役になっていないか。声に出して読み下せるか。
5. **主語テスト**: 手順の各ステップで、ユーザーがやることとスキルがやることが区別できるか。
6. **切り出しテスト**: 注意事項の各行を単独で読んで意味が取れるか。
7. **前提テスト**: 前提条件が「起動時に必要なもの」だけになっているか。自明な環境前提・許可の記述・途中条件が混ざっていないか。
8. **具体例テスト**: 依頼文と成果物のペアがあり、成果物側が種類の列挙ではなく中身の抜粋になっているか。具体例を消すと出力の粒度が分からなくなる状態が合格。
9. **リンクテスト**: 関連スキルの各行にリンクがあり、移るべき場面が書かれているか。
