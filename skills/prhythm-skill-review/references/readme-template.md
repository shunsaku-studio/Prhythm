## 概要

最初の 2〜3 文で、何を入力すると何が出てくるかを書く。独自用語を使うならここで一度定義する。

{何を渡すと、何が返ってくるか。}

## 利用メリット

手作業や素の LLM と比べて、ユーザーの作業や判断がどう楽になるかを書く。概要の言い換えや、スキル内部の設計特性は書かない。

- {初めてのヒアリングでも、重要な点を押さえた質問紙を準備できる}
- {参考サービスを地図上に並べるので、競合がひしめく領域とまだ誰もいない領域をチームで議論できる}

## 利用シーン

ユーザーが実際に置かれる具体的な状況だけを書く。末尾に、打ち込む依頼文を 1〜2 個添える。

- {初回ヒアリング前に何を聞くか整理したいとき}
- {差別化の置き場が曖昧で、いきなり画面に落とす前に市場の見取り図が欲しいとき}

依頼の例: 「{ユーザーが実際に打ち込む文}」

## 使い方

工程に対していつ使うかを 1 段落で書く。続けて番号付き手順。各ステップは、ユーザーがやることとスキルがやることを主語で区別する。途中の合意や確認は、前提条件ではなく該当ステップに書く。

**いつ使うか:** {会議前に mode:prep を、会議後に mode:analysis を使う。直前に済ませていることが多いスキルがあれば 1〜2 個。}

1. {ユーザーが材料を渡し、スキルが草案を出す}
2. {チームが草案を見て決め、スキルが次の成果物を書く}

## 具体例

「使い方」の直後に置く。依頼文 1 つと、成果物の中身の抜粋のペア。抜粋は種類の列挙ではなく、実際の名前が入った表の 2〜3 行、成果物中の一文、数行の図など。example.md があるスキルは最小抜粋の末尾でリンクする。

依頼: 「{実際の依頼文}」

表と Mermaid はコードブロックで囲まず、ドキュメントサイトが描画できるように素の Markdown で書く。コード（SDL、ディレクトリツリー）だけフェンスを残す。抜粋は `::: info 〜の抜粋:` で囲み、見出し行はコンテナのタイトルにする。表の末尾には `...` の行を足して、続きがあることを示す。

## 前提条件

起動時に必須な入力・環境・条件だけを、何がどう必要なのか文で書く。スキル集全体で自明な実行環境と、「〜でも使ってよい」は書かない。プロセス途中の条件は使い方へ移す。

- {日英での Web 検索が実行できる環境が必要}
- {対象となる RFC / 提案 / brief などのテキスト}

## 注意事項

使って初めて気づく非自明な落とし穴だけを、因果の通った文で書く。残すものが無ければこのセクションごと削除する。

- {Slack ボットのような非公式チャネルで提供されるサービスは Web 検索から漏れやすい。調査に含め忘れると、実際には競合がいる領域が空白に見えてしまう}
